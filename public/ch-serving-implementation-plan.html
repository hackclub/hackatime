Implemented foundation

  • HeartbeatIntervals::Calculator computes all filter sequences in one ordered pass.
  • heartbeat_interval_deltas is append-only and carries positive and negative corrections.
  • ClickHouse materialized views maintain user, project, filter, attribution, and project-detail tables.
  • Clickhouse::StatsReader routes supported product reads to the smallest serving grain.
  • HeartbeatIntervals::UserLock serializes each user's classify, write, and correction sequence across threads and Rails processes.

What we should not build

  • Do not run OPTIMIZE FINAL after writes.
  • Do not put materialized views directly on raw heartbeats for duration math.
  • Do not expect projections on the raw table to fix tombstone correctness or neighbor-dependent intervals.
  • Do not use one aggregate for both filter semantics and attributed breakdown semantics.

Implemented Architecture

Raw heartbeats remain canonical. On direct appends Rails emits small interval deltas immediately, using one predecessor read for a multi-heartbeat batch. Retries emit nothing; equal-time or late rows, tombstones, and imports rebuild the affected user's net facts. Account merges complete the canonical move in-request, then enqueue one globally serialized rebuild for both users so a multi-minute correction cannot hold the admin request open. Per-user locks make classification and correction atomic with respect to other Rails writers. A failed post-insert delta write durably enqueues recovery. ClickHouse receives only append-only corrections and maintains all rollups itself.

Why Not a Raw Materialized View?

ClickHouse materialized views are useful, but duration is not a simple per-row aggregate. A heartbeat's duration depends on the next current heartbeat, and raw rows can later be replaced or tombstoned.

The neighbor problem

A materialized view on heartbeats sees inserted blocks. It does not naturally know that inserting heartbeat B between A and C should subtract the old A-to-C interval and add A-to-B plus B-to-C. That recomputation boundary is domain logic, so it belongs in a builder.

The replacement problem

If a raw heartbeat later gets a tombstone or newer version, a naive aggregate materialized view has already counted the old contribution. ClickHouse merges in the source table do not automatically retract values already inserted into a target table.

The rule

Use ClickHouse materialized views after we have an append-only, correction-aware fact stream. Do not use a materialized view directly on versioned raw heartbeats for final product stats.

ClickHouse Tables

The schema separates filter duration from attributed breakdown duration. That distinction is required for parity with the old code: filtering by Ruby computes gaps within Ruby rows, while a language chart attributes normal user or project gaps to the current row's language. Filter grains also preserve NULL and empty-string buckets separately; attributed grains omit both, except that project entities retain the empty bucket for the legacy distinct-file count.

Correction fact sketch

CREATE TABLE heartbeat_interval_deltas
(
  user_id UInt32,
  day Date,
  time Float64,
  project LowCardinality(String),
  language LowCardinality(String),
  user_seconds_delta Float64,
  user_first_seconds_delta Float64,
  project_seconds_delta Float64,
  language_seconds_delta Float64,
  heartbeat_count_delta Int64,
  reason LowCardinality(String)
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(day)
ORDER BY (user_id, day, time, delta_id);

Why SummingMergeTree is correct here

The materialized views do not read versioned raw heartbeats. They consume an append-only stream where Rails explicitly retracts stale contributions. Reads always use sum(...), so correctness does not depend on physical background merges and does not require FINAL.

Pre-production load mechanics

  • Enumerate live users by keyset-paginated user_id and enqueue bounded batches.
  • Backfill through server-side UserRebuilder so each user starts with one compact net correction set without Rails loading every heartbeat.
  • Let incremental materialized views populate every serving table from that fact stream.
  • Use GoodJob state for batch progress and START_AFTER to resume enqueueing from a known user ID.

Risks and Design Decisions

The main risk is not ClickHouse performance. It is double counting or stale summaries when a late heartbeat, tombstone, or account merge changes an already-counted interval.

Late heartbeats

They can split a previous interval. The writer detects non-appends and rebuilds one compact net fact set for that user.

Soft deletes

Deleting or restoring a heartbeat can merge or split intervals. Both changes trigger the same user-level correction rebuild.

Account merges

Merges change user_id, which is the leading key. The canonical move is locked and synchronous; one HeartbeatServingRebuildJob then rebuilds source and destination. It shares a global concurrency key with backfills, while ClickHouse emits each user's net correction in one insert. If enqueueing fails, Rails performs the correction synchronously.

Concurrent retries

Classification cannot race another write for the same user. Rails takes a reentrant process-local lock and a cross-process PostgreSQL advisory lock around classification, insertion, and correction.

Adapter concurrency

The ClickHouse adapter keeps a persistent HTTP connection and mutable response format. A per-connection reentrant monitor prevents shared system-test or async callers from interleaving requests while preserving pool-level concurrency.

Large rebuilds

Rebuild queries use one thread, 64 MiB external sort/group thresholds, and a scoped five-minute read timeout. A clean 3.3-million-heartbeat rebuild completed in 233 seconds without exhausting the local server.

Correction history

Each rebuild groups existing facts with the current canonical replay and inserts only nonzero differences. An unchanged rebuild is a no-op, so retries do not multiply correction history; genuine mutations append only the groups that changed.

Request latency

Supported whole-day stats paths sum summary rows or read project snapshots. Raw interval work remains explicit only for semantics the current grains cannot represent.

Debuggability

Keep interval facts inspectable. If a summary looks wrong, engineers should trace it to exact interval rows.

Future MVs

Materialized views consume only the correction-safe fact stream, never the versioned raw heartbeat table.
