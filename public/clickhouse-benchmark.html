Methodology and limitations

Each query ran five times per system after ClickHouse parts were merged to a steady-state layout. The report records first-run latency and nearest-rank p50/p95 wall-clock latency. ClickHouse read volume comes from system.query_log; PostgreSQL read volume comes from a sixth EXPLAIN ANALYZE run with BUFFERS and counts logical 8 KiB buffers. Ordered results are canonicalised at each query's declared output precision and SHA-256 fingerprinted without retaining values. User-scoped families run for every cohort and global families use all sampled rows.

Recent windows are anchored at sampled max(time), except the explicit dashboard date filters, which use each cohort's populated 30-day range: 1786521221.458. PostgreSQL read volume is logical 8 KiB buffers, not physical bytes. Cache state is not reset. Production ClickHouse ingest measures full repository admission: locks, canonical state, aliases, both query layouts, visibility checks and delivery acknowledgement. The PostgreSQL ingest baseline is one local table insert, so it understates equivalent deduplication and durability work. Replacement retries and concurrent failures are covered by ClickHouse integration tests. Export and account lifecycle timings measure their source scans. This is a 6-user shape benchmark, not a concurrency or full-production-cardinality test.

Implemented architecture

The production layout keeps full-resolution time and adds only the materialized second and five-minute buckets used by query pruning and sorting. User-scoped reads use (user_id, time_5m, time_second, time, id). A replacement-aware physical mirror ordered by (time_5m, time_second, user_id, time, id) serves recent cross-user reads because ClickHouse cannot use an alternate-order projection with FINAL. Exact timestamp predicates run after bucket pruning on both tables. A ClickHouse text index accelerates user-agent substring searches.

Rails callers use HeartbeatRepository. ClickHouse heartbeat_store owns canonical payload and lifecycle state, while heartbeat_aliases owns exact canonical and legacy hash deduplication. Independent delivery versions repair either query layout after an interrupted write. PostgreSQL retains only monotonic sequences, transient advisory locks and coarse lifecycle workflow status. Dashboard, profile and exact homepage totals query ClickHouse directly; PostgreSQL dashboard rollups are neither read nor rebuilt after cutover.

Decision

Selected ClickHouse design: ClickHouse production routing.

Every sampled dashboard query matched PostgreSQL and stayed within a 250 ms p95 budget on ClickHouse production routing. Precomputed heartbeat rollups are unnecessary. Homepage totals also run as an exact ClickHouse query with relational archived-project exclusions supplied as a filter set.
